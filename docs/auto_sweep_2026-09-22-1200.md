## Increment
Phase 3 skeleton — the proposer/verifier loop, "the middle loop; the product." `tools/improvement_loop.py`.

## The loop
`propose → verify (fresh context, frozen holdout, PROCTOR) → accept iff grounded risk strictly decreases AND
prediction held AND blast radius did not widen AND canary consistent → promote via harness_registry.set (with a
post-promotion recoverability check) or revert + log`. Verdict carries the four fields.

## Synthetic task (computed pass/fail)
The harness under test is a `context/compaction` policy. Held-out set: frozen context bundles (rule / identity /
episodic / search_result over a budget). Grounded risk = fraction of `rule` items lost (`concept_compaction_cliff`).
- Good proposal (pin rule + identity): risk **0.18 → 0.00**, accepted, recoverable.
- Bad proposal (pin nothing): risk **0.00 → 0.18**, `strict_decrease` false → **rejected**. The plan's
  non-negotiable negative test.

## Verifier spec → code
Fresh context (verifier takes policies + prediction, never the proposal text); frozen holdout the proposer never
reads; all-`rule` canary where acing it without pinning `rule` is impossible; `authority` field names the
holdout not the proposer; grounded strict-decrease acceptance (`pattern_grounded_acceptance_only`); blast-radius
widening check; EvoUndo-style recoverability check; four-field verdict carry (`pattern_four_field_constraint`).

## Two real bugs caught this run
1. **Flaky condensation (experience_bank).** `condense()` ordered a critique→correction check by `ts`, and
   consecutive events can share a timestamp at `round(time.time(), 6)` resolution — so the step lesson was
   sometimes not created. The full-suite runner caught it (the module's own selftest had passed on a lucky
   run). Fixed to order by list position.
2. **Schema gap.** Added `seq` — a monotonic per-run counter — to every event as the *reliable* order key, with
   a validator check. `ts` is kept for wall-clock but is no longer load-bearing for ordering.
