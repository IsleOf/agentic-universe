`concept_tool_call_reliability_is_a_non_atomic_failure_problem_idempotency_keys_and_verify_before_retry_not_a_better_model`

Core: real tool calls are not atomic — timeout-after-dispatch, delayed
visibility, partial state updates make an agent think a call failed when it
partly succeeded, so it retries and duplicates the action. Fix is a
verification-aware wrapper (postcondition check, verify-before-retry, idempotency
keys), not a stronger model. Model-independent by design; controlled-sim
evaluation, no headline number in the abstract → `verification_state:
abstract_read`.

Edges:
- `extends` → the PILOT task-ledger pattern (that makes *dispatch* idempotent;
  this makes the *tool call* idempotent, one layer down)
- `grounds` on `observation_an_idle_prompted_agent_session...` — this session's
  own non-atomic failures: the agy-real bootstraps that sent READY then hung
  (delayed visibility), the killed worker whose file writes survived (partial
  state update)
- `informs` the capability-token node — a fenced lease says "you no longer hold
  this", an idempotency key says "you already did this"; a coordination layer
  needs both
- `supports` the code-owned-enforcement node (the wrapper decides retry safety,
  not the model)
- `refines` the "pass/fail overcredits lucky retries" node — some of those
  retries are not lucky but *harmful* duplicates the success metric hides
- `supports` the cascade-radius / per-mode-recovery node (a named failure mode
  with a named recovery)
