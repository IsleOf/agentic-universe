## The one that moved
`test_scenario_decomposition_granularity` — the pilot (arXiv:2608.23395) left the "intermediate decomposition
granularity is optimal" hypothesis unsupported at pilot scale. Three 2026 papers now reframe the question:

- **arXiv:2606.00953 (Co-Coder, May 2026)** — decomposition shortens the critical path but cross-agent
  dependencies force costly context transfer; gains are largest on dependency-dense projects, and community
  detection decides where to split. Granularity is a function of task structure, not a fixed number.
- **arXiv:2608.19557 (Aug 2026)** — a multi-agent control plane beats a static heuristic *only* "when
  non-stationarity opens headroom a fixed policy cannot use." Under stationary load, extra orchestration adds
  nothing.
- **arXiv:2605.05007 (Uno-Orchestra, May 2026)** — selective, learned decomposition depth beats any fixed
  routing strategy.

Net: the universal "intermediate optimum" claim stays unsupported, but the surviving result (single agent does
not Pareto-dominate the orchestrated set) holds, and the refinement is that decomposition depth should be
**chosen per task from dependency density and non-stationarity**, not fixed. All three are abstract-reads;
two predate the 30-day window and are dated accordingly.

## Consistency note for the design
`nourishing_harness_design.md` §3.1 answers geometric decay with "decompose aggressively." Run 50 adds an
`informs` edge to `concept_geometric_reliability_decay`: aggressive splitting of a *dependency-dense* task moves
cost into context transfer rather than removing it — the decomposition has to read the task's dependency
structure, which is exactly the concern `what_would_make_this_wrong.md` §5 already carries ("the decomposition
just moves the compounding failure from steps to handoffs"). This is not a new failure mode, it's a sharper
statement of an open one.
