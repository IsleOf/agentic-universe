## The drift
`skill_induction.classify()` maps an increment to a task class and falls back to `other`. It
**always returns a label**, so it never looks broken. Over ~30 runs the loop's writing style
moved — bare `"fold <arxiv id>"` instead of `"folded in"`, `"wire A to B"` and `"build x.py"`
instead of `"tools/"` — and an entire task class appeared that the taxonomy predated:
**per-project audits** (poly-bot, poster-studio). Result: 33.6% of the corpus silently in
`other`.

New keywords were derived by **reading the unclassified increments**, not by aiming at a
distribution. Added a `project audit` class.

## The honesty work — three bounds, now in the docs
1. **Spot-check.** Against 26 runs whose true class I know: **22/26 (85%)** agreement. The
   named failure mode is that verification and adversarial passes leak into `build` — run
   364's own record classifies as `build`, partly because its increment text *mentions task
   class names*. So 76.7% modestly **over**-states; the defensible claim is a **70–77% band**,
   not a point estimate.
2. **The axis mapping** (which classes are elicitation- vs capability-shaped) remains
   judgement, not measurement.
3. **I predicted the direction before measuring it.** That is a bias risk. Mitigation was to
   derive keywords from the unclassified text first; it is not eliminated, and the reader
   should weigh it. Recorded in the node and both docs.

## The durable fix
A **classifier-drift guard** in `skill_induction`'s selftest: it classifies the live run
corpus and **fails the build if `other` exceeds 15%**. The next vocabulary drift turns the
build RED instead of quietly making every task-class measurement rougher. Non-hermetic by
necessity; skipped below 50 runs.

## The general finding
New node: **a classifier with a fallback bucket never reports that it has stopped working —
it just widens the bucket.** The failure mode is a *label*, not an error. Guard it by
asserting the fallback rate against live data.

This is the **sibling** of run 361's bug, found one run later: there, a metric nobody
remembered to populate; here, a metric always populated with a fallback. Same family — an
instrument returning a plausible value while measuring nothing. Both were found by *running
the instrument over real data* rather than reading its output.

**The uncomfortable corollary**, recorded in the node: fixing the instrument strengthened a
conclusion that is *bad news for this project's own bet*. A drifted instrument is dangerous in
both directions — it can hide a finding you would want, and one you would not.
