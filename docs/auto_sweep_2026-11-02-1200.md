**arXiv:2609.04280 — EVOHARNESSBENCH: Can Your Agents Keep Pace with an Evolving Harness?**
(Ke, Patil, Shi et al., Salesforce AI / UNC, 2026-09-03.)

## The design choice that makes it land
Existing continual-learning benchmarks put the non-stationarity in the **task stream** and hold
the harness fixed. This one puts it in the **externally supplied harness itself** — tools,
skills, and specialist agents. 17 multi-stage streams, 802 tasks, 520 tools, 42 skills, 62 agents.

Three persistent gaps:

1. **Harness expansion alone can degrade performance on previously solved tasks** —
   harness-induced forgetting, with no task change and no policy change.
2. Adaptation gains are inconsistent across stages, axes, and environments.
3. **Retention and adaptation pull in different directions.** Preserving earlier competence
   doesn't necessarily improve adaptation to new capabilities, or vice versa.

This loop *is* an evolving harness, on all three of those axes, and has been for 388 runs. It
adds tools, induces skills, and registers probes and selftest jobs on its own initiative.
Finding (1) says that isn't a free action.

## So I checked whether this project would notice
It has the right instrument: the frozen `holdout_tasks` set, a second independently-implemented
scorer in `holdout_verifier2`, and `improvement_loop.verify_loop_edit`, which rejects on
regression and treats verifier disagreement conservatively. That's good machinery.

**It is wired to the wrong event.** `verify_loop_edit` has exactly one non-test call site:
`acceptance_gate.check()`, which adjudicates **proposals** — graph patches and policy edits.
Adding a file to `tools/`, an arm to a probe, or a job to `selftest_all`'s JOBS never reaches it.
(`exec_guard` watches JOBS for *shrinkage*, so removal is guarded; **addition is not.**)

The gate log holds 183 entries, **none from these six runs**. Harness expansion on all three

## The honest counterweight
The gap is narrower than that makes it sound. **`selftest_all` IS a retention instrument**, and
a real one — 51 jobs re-run every single run is structurally the paper's *deployment
evaluation*, and it has stayed GREEN throughout.

What it measures is **component self-consistency**: everything still passes its own tests. What
it can't measure is **task competence** — whether the loop still chooses well now that it has
more tools to choose among. A tool can keep passing its own tests while the system around it
gets worse at using it.

That's exactly the paper's two settings, and this project has the first and not the second.

Finding (3) also has a local instance, made by instinct rather than measurement: run 385 added
an adaptive threshold (**adaptation**) while defaulting `signal_correlation=0.0` so existing
behaviour stayed bit-identical (**retention**). The paper says that tension is real and doesn't
resolve itself — which supports the caution, and also says the judgement was unmeasured.

## What I built, and what I deliberately didn't
**Didn't:** wire harness expansion into the retention gate. That's a change to the loop's own
acceptance path and belongs behind the owner's promotion step, not in the run that noticed the
gap. The loop rewriting the conditions under which it is allowed to accept its own work is the
one edit it shouldn't make unsupervised.

**Did:** make the gap *visible per run* instead of silent. `loop_session._harness_delta()` now
records, in every run summary, whether the run touched `tools/`, `skills/` or `runtime/harness/`,
which files were new, and whether the certificate log actually **grew** during the run —
`unevaluated_expansion` when it expanded and didn't.

`retention_evaluated` asks whether the log *grew*, not whether a gate exists. An instrument
reporting on its own behalf is precisely how run 368's accept-only log happened. A missing or
unreadable log reports **not evaluated** — the conservative direction, since the claim at stake
is "this expansion was checked."
