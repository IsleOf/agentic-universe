Week-1 build list **item 6, the last one**: `tools/swarm_demo.py` — the acceptance test for the

## What it is
`run(goal)` is a `while` loop that:
1. reads `ledger.next_ready()` (by stage),
2. asks `reputation.select()` who takes it — **excluding the task's own contributors**, so gates
   stay valid and work gets fresh eyes,
3. lets that agent `contribute()`,
4. drops the contribution on the **pheromone board** (not a private channel),
5. runs **G1** after research, **G4** before done,
6. `relay.handoff()` to the next stage.

The loop holds **no decision state** — it's the deterministic substrate, the same shape as
`fractal_flock.run()`. A selftest regex asserts there is no `Orchestrator` / `Chief` / `Boss` /
`Manager` class in the module. `contribute()` is the caller's generative work; the shipped
`_fake_worker` makes no model calls.

## A live run
```
research (a1) → G1 (a2, pass) → draft (a2) → critique (a1) → final (a2) → G4 (a3, pass, quorum 2) → RELEASED
```
Different agents per stage, validators never the contributor, clean audit trail.

## The finding: a gated pipeline needs ≥ 3 agents
The no-self-review rule (run 395: a validator may not have contributed to the artifact) plus a
4-stage pipeline sets a hard floor. **At k=2**, by the time an artifact reaches G4 both agents
have contributed to some stage, so `reputation.select()` over non-contributors returns nothing
and the gate raises `GateRefused`. The run then **fails cleanly** — a `GateRefused` entry in the
transcript, no exception, no hang — rather than silently releasing an unreviewed artifact.

This isn't a bug; it's the rule working. But it means the design's stated **"2–15 agents" is
"3–15" for gated work**. A 2-agent fleet can still coordinate through the board and ledger for
*ungated* tasks. Recorded as a graph node, not papered over.

**General shape:** any quorum or rotation rule imposes a minimum population of
`(exclusion count) + (required count)`. Worth stating whenever "works with N agents" is claimed
about a system that also has gates.
