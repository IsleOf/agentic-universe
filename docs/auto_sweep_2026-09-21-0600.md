`tools/task_ledger.py` + `docs/task_ledger.md` — a **deterministic task ledger** the orchestrator reads
and writes instead of the model holding task state in its context. Motivated by two folded findings:
`concept_component_lifecycle_reasoning_degrades_with_size` (CordisBench — LLM state-reasoning degrades with
system size; a finite reference semantics matches execution exactly) and `concept_aspire_...` (continued
open-ended search erases earlier gains).

One row per task; statuses `pending → active → done` (+ `blocked` / `failed` / `abandoned`). Three
anti-dropped-task mechanisms:

1. **`next_ready()` is deterministic** — the oldest `pending` task whose deps are all `done`; the
   orchestrator *reads* its next action instead of reasoning about it.
2. **`sweep_stale(max_active_secs)`** — a task `claim`ed but never finished within a timeout goes back to
   `pending` (worker died / lost context / hit budget) — the PILOT supervisor re-dispatch pattern.
3. **atomic write** (`os.replace`) + an append-only `<ledger>.audit` log per mutation.

Pure stdlib, **not wired into the loop** — a drop-in reference implementation for the owner's
orchestrations (poly-bot etc.): copy the one file, replace "ask the LLM what to do next" with
`L.next_ready()`, call `L.sweep_stale()` each tick, keep the ledger in a durable path.
