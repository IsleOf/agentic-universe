# Autonomous sweep — 2026-10-29 18:00 (run 371)

## Increment
Acted on the design gap run 370's WorldBench fold exposed: **the gate scores whether an edit
helps, never what it disturbed.** First non-instrument design work in eleven runs.

## Confirmed by reading, not assumed
`acceptance_gate.check(proposal, ...)` passed `proposal` to `proposal_digest()` **and nowhere
else**. Every accept/reject term came from `baseline_scores` vs `candidate_scores`. The gate
had no notion of what a patch touched.

`improvement_loop.blast_radius` exists — but it applies only to *context-policy* edits
(pin/compress classes) and only when `edit` is supplied. It never sees a graph patch.

## The sharp version — a latent vulnerability, not a missing nicety
The graph-patch contract is **add-only** (`proposal_metadata` / `add_nodes` / `add_edges`).
But `knowledge_graph.check_patch` **silently ignores keys it doesn't recognise.** So:

```python
{"proposal_metadata": {}, "add_nodes": [], "add_edges": [],
 "remove_nodes": ["concept_anchor"]}        # -> check_patch returns []  (valid!)
```

Nothing would have *honoured* that today — no current `apply_patch` reads those keys — but
nothing would have **objected** either, and the gate is precisely the component whose job is to
object.

## What was added
`modification_footprint(proposal)` → rides on **every** certificate, accept or reject:

| field | meaning |
|---|---|
| `added_nodes` / `added_edges` | the intended growth |
| `touch_surface` | distinct **pre-existing** node ids the new edges attach to — a patch wiring into 30 unrelated nodes isn't minimal even though it deletes nothing |
| `destructive_keys` | any key whose name implies mutation or removal |
| `unknown_keys` | anything else outside the contract — **reported, not fatal** |

**One hard refusal:** a patch carrying a destructive key is rejected *before* the held-out
comparison, and the refusal is logged like any other adjudication (run 368) so a blocked patch
leaves a trace rather than vanishing.

The selftest asserts that `check_patch` **really does** let such a patch through — so if the
validator is ever tightened, this justification fails loudly instead of going stale.

## A brittle assertion of my own, found and fixed
Run 368's check `a rejected edit IS appended` used a hard-coded `== 2` line count, and broke
the moment this run added another logged rejection earlier in the selftest. Made relative to a
before-count. That is exactly the brittleness this file keeps finding elsewhere — worth noting
that it was mine, two runs old.

## What is still unmeasured — stated, not papered over
- `touch_surface` is **reported but not thresholded.** There is no principled cap on how many
  pre-existing nodes one patch may wire into, and inventing one would be worse than reporting
  the number.
- The environment this loop actually modifies is **the repository**, not just the graph.
  Nothing scores collateral file changes.
