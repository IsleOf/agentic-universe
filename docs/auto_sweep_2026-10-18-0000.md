## What it shows
Tools normally must be hand-implemented — a bottleneck for domains needing many specialised tools.
**ToolMaker** autonomously turns a paper-with-code (GitHub URL + task description) into an LLM-compatible
tool: installs dependencies, generates code, **debugs via closed-loop self-correction**. Benchmark: 15
tasks, 100+ unit tests; **80% correct**, substantially beating SOTA software-engineering agents.

## Why it matters
- **The harness's *action* layer can be self-extended** — not just its context (ACE) or its skills
  (Phase 4 skill induction). The Phase 1 registry versions tools as artifacts; ToolMaker is the generator
  that would feed it. Recorded as `supports` `artifact_phase1_harness_registry`.
- **The unit-test gate + closed-loop self-correction is `pattern_grounded_acceptance_only` applied to the
  action layer** — a tool is accepted iff its executable tests pass, not on a self-report.
- "action" is one of the six runtime responsibilities (`concept_bottleneck_is_the_model_harness_coupling`),
  and this is the **least-explored** of the six for self-modification.
- **Caveat (in the node):** a self-written tool is new arbitrary-code-execution surface, and tool
  *generation* (dependency install, code exec, debugging) is itself privileged — the exec layer
  (`pattern_execution_layer_enforcement` / Phase 5) must cover the tool-making loop, not just tool use.
  Recorded as `challenges`.
